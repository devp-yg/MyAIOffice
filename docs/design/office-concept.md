# My AI Office: 넓은 공용 오피스 구상

## 한 줄 요약

프로젝트 폴더마다 층을 만들지 않고, 여러 프로젝트의 직원이 **하나의 넓은 공용 오피스**에서 함께 일하는 모습을 보여준다. 공간은 프로젝트별이 아니라 자료 탐색, 개발, 실행·서버, 검토·회의, 휴식 같은 **공통 업무 프로세스**를 기준으로 나눈다.

## 배경과 의도

현재 구현은 프로젝트 폴더 하나를 건물 한 층에 대응시킨다. 프로젝트가 늘수록 층이 많아지고, 여러 프로젝트의 동시 작업을 한눈에 보기 어렵다. 프로젝트를 사람이 직접 묶고 유지하는 방식은 별도의 관리 부담을 만든다.

초기 저장 시안 `previews/office-v1.1.png`는 한 층 안에 자료실, 개발실, 서버실, 정보검색실, 회의실, 대기 공간을 배치했다. 이 업무 공간 구조를 살리고, 프로젝트는 층이 아닌 작업자와 세션의 소속 정보로 표현하는 방향을 제안한다.

## 설계 원칙

1. **프로젝트는 자동 식별한다.** Codex의 프로젝트 폴더 정보를 사용하며 사용자가 프로젝트를 직접 묶거나 층을 지정하지 않는다.
2. **공간은 업무 프로세스를 나타낸다.** 프로젝트가 달라도 같은 종류의 일을 하면 같은 업무 구역에 나타난다.
3. **동시 작업을 한 화면에서 보여준다.** 서로 다른 프로젝트의 직원과 진행 상태를 공용 오피스 안에서 함께 볼 수 있다.
4. **프로젝트 맥락은 계속 드러낸다.** 직원 이름표, 작은 색상 표식, 상세 정보에 프로젝트명을 표시한다. 색상만으로 구분하지 않고 텍스트도 함께 제공한다.
5. **규모는 가구와 공간으로 흡수한다.** 작업자가 늘면 구역별 책상과 자리를 늘리고 열린 이동 공간에 충분한 여유를 둔다. 표시 인원 수에 고정 상한을 두지 않는다.
6. **전체 보기와 집중 보기를 함께 둔다.** 기본 화면은 전체 층을 보여주고, 방이나 직원을 선택하면 해당 위치로 확대해 자세히 살펴본다.

## 공간 구성 초안

- **자료·조사 구역:** 문서와 참고 자료를 읽고 검색한다.
- **개발 구역:** 여러 개발 책상과 모니터를 두고 코드 작성·수정 작업을 보여준다.
- **실행·서버 구역:** 빌드, 명령 실행, 서버와 도구 작업을 표현한다.
- **검토·회의 구역:** 결과 확인, 계획 정리, 토론과 협업을 보여준다.
- **휴식·대기 구역:** 진행 중인 작업이 없는 직원이 머문다.
- **중앙 정원과 열린 순환 동선:** 직원들이 여러 경로로 업무 구역을 오가고, 중앙 공간은 만남과 휴식의 장소가 된다.

구역 이름과 분류는 현재 앱의 업무 분류를 바탕으로 조정한다. 새 프로젝트가 추가되어도 건물 층이나 공간을 새로 만들지 않는다.

## 화면 동작 제안

- 기본 화면은 전체 층을 조망하는 축소 시점으로 시작한다.
- 직원이나 업무 구역을 누르면 카메라가 자연스럽게 확대된다.
- 프로젝트 이름 검색 또는 선택은 기존 프로젝트 목록에서 제공한다. 이는 보기 필터이며 별도의 프로젝트 묶음 설정을 요구하지 않는다.
- 필터가 꺼지면 전체 프로젝트의 동시 작업을 다시 보여준다.
- 겹침을 줄이기 위해 각 업무 구역에 여러 작업 포드와 좌석을 두고, 이름표는 선택 직원이나 작업 중인 직원 위주로 표시한다.
- 화면 크기와 동시 작업량에 맞춰 카메라 기본 줌을 조절한다. 직원이 많아도 전체 층 화면에서 직원이 지나치게 작아지면 구역 단위로 이동해 볼 수 있게 한다.

## 다음 설계 단계

1. 실제 Codex 작업 분류와 각 공간의 대응 관계를 검토한다.
2. 대표적인 동시 인원 규모를 정하고 책상 수, 통로 폭, 이름표 밀도를 잡는다.
3. 현재 프로젝트별 층 데이터 모델을 공용 오피스·프로젝트 소속 표시 방식으로 바꾸는 범위를 설계한다.
4. 전체 보기와 구역 확대 상태에서 직원 선택, 프로젝트 필터, 카메라 이동을 구체화한다.
5. 작은 화면에서의 배치와 많은 직원이 있을 때의 가독성을 확인한다.

이 문서는 대화에서 나온 방향을 정리한 개념안이다. 실제 구현 전에 직원 수와 업무 구역 분류를 기존 세션 데이터로 대조해 구체화한다.

## 현행 앱의 업무 분류와 공간 대응

현재 `server-records.mjs`는 Codex의 마지막 활동을 여섯 가지 방 키로 분류한다. 물리 공간은 아래처럼 가까운 업무를 합쳐 다섯 구역으로 표현할 수 있다. 세부 분류는 상태와 상세 정보에 보존한다.

| 현행 분류 | 현재 감지하는 일 | 공용 오피스 구역 |
| --- | --- | --- |
| `library` | 파일과 자료 확인 | 자료 탐색 |
| `research` | 웹 검색과 도구 사용 | 자료 탐색 |
| `studio` | 코드와 파일 수정 | 개발 |
| `server` | 터미널과 명령 실행 | 실행·서버 |
| `meeting` | 계획 정리, 에이전트 응답 | 검토·회의 |
| `elevator` | 서브에이전트 협업 신호 | 검토·회의로 이동/협업 표시 |
| `desk` | 새 요청 접수, 일반 활동, 비활성 세션 | 요청 접수·휴식·대기 |

`library`와 `research`는 같은 자료 탐색 공간의 서로 다른 자리로 배치한다. `meeting`과 협업 신호도 한 협업 구역 안에서 표현한다. 현재 분류를 새 프로젝트별로 복제하지 않고, 작업 세션의 프로젝트 식별자(`projectKey`)는 계속 보존한다.

## 데이터 구조에서 확인한 점

- 서버는 각 세션에 `projectKey`, 프로젝트명, 업무 분류, 활동 시각을 이미 붙여 보낸다. 따라서 프로젝트 폴더 수동 그룹 없이 전체 프로젝트의 세션을 한 화면에 모을 수 있다.
- 현재 화면은 선택된 프로젝트 키로 세션을 먼저 제한한다. 공용 오피스에서는 기본 목록을 전체 세션으로 바꾸고, 프로젝트 선택은 보기 필터 또는 강조로 처리하면 된다.
- 프로젝트 식별은 폴더 경로에서 해시를 만든 값이라 화면에는 경로가 노출되지 않는다. 프로젝트 이름은 칩과 상세 정보에 표시할 수 있다.
- 현재 렌더링은 방당 보통 최대 3명, 전체 층 최대 11명으로 제한한다. 작업 위치도 방마다 3개 안팎의 좌석 배열을 반복 사용하므로, 단순히 화면 제한만 제거하면 캐릭터가 같은 지점에 겹칠 수 있다. 바닥 면적, 좌석 생성, 경로 지점, 이름표 밀도를 함께 설계해야 한다.

## 데이터 크기 관찰

2026-10-21에 로컬 앱 상태를 집계했을 때, 등록 프로젝트 24개와 최근 세션 36개가 있었고 그 순간 활성 세션은 1개였다. 이는 층 수 문제가 실제로 이미 생길 수 있음을 보여주지만, 한 시점의 활성 수만으로 최대 동시 작업량을 정하기는 어렵다.

따라서 첫 공간안은 **약 42명까지 동시에 자리 배치가 가능한 크기**를 기준점으로 삼고, 특정 구역에 작업이 몰리면 해당 구역에 작업 포드를 추가하는 방식으로 잡는다. 전체 건물의 프로젝트 수와 활성 직원 수는 다른 값이므로 별도로 표시한다.

## 다음 화면의 표시 규칙

- **전체 보기(기본):** 모든 프로젝트의 활성 세션을 업무 구역별로 배치한다. 프로젝트명은 직원 이름표의 짧은 칩으로 자동 표시한다.
- **프로젝트 집중:** 프로젝트 검색 목록에서 하나를 고르면 해당 프로젝트 직원을 선명하게 보여주고 나머지는 숨기거나 낮은 대비로 둔다. 별도의 프로젝트 묶음은 만들지 않는다.
- **업무 구역 집중:** 방을 고르면 해당 업무를 하는 세션과 상태를 상세히 본다. 직원 선택 시 카메라가 그 직원을 따라 확대한다.
- **휴식 세션:** 프로젝트마다 가장 최근의 비활성 세션 하나를 대기 구역에 둘 수 있다. 나머지 비활성 세션은 팀 목록에서 확인하고, 대기 인원 수로 요약한다.
- **이름표 밀도:** 전체 보기에서는 이름과 프로젝트 칩을 선택·활동·이동 중인 직원 위주로 표시한다. 확대 보기에서는 선택 구역의 이름표를 늘린다.

## 평면 크기와 좌석 초안

현행 표준 층의 이동 범위는 약 27 × 16m다. 개념 설계에서는 이를 약 **40 × 24m**로 키우고, 중앙 정원과 그 주위를 감싸는 열린 순환 동선을 둔다. 아래 수치는 실측이 아니라 첫 3D 배치 검토를 위한 목표다.

- 자료 탐색: 6자리
- 개발: 12자리
- 실행·서버: 6자리
- 검토·회의: 12자리 (4인 테이블 3개)
- 요청 접수·휴식·대기: 6자리
- 기준 배치 합계: 약 42자리

업무 분포는 개발 구역에 더 많은 자리를 주되, 실제 세션의 업무 분류 빈도를 확인해 조정한다. 이 수치는 기준 배치일 뿐 구역별 고정 상한이 아니다. 혼잡하면 층을 추가하는 대신 해당 업무 구역의 포드를 늘린다. 자리가 찬 구역은 기존 프로젝트 좌석을 옮기지 않고, 주변 가구를 재배치하거나 같은 구역에 포드를 더해 확장한다. 동선은 고정된 폭의 복도보다 여유 있는 열린 연결 공간으로 만든다. 전체 보기에서 캐릭터가 너무 작아지지 않도록 기본 카메라는 약간 높은 아이소메트릭 시점으로 맞추고, 구역과 직원 클릭 시 확대한다.

## 아직 결정할 구현 항목

- 프로젝트 이름 칩의 색상과 길이 제한, 이름이 겹칠 때 표기 방식
- 전체 보기에서 나머지 비활성 세션을 몇 개까지 대기 구역에 보여줄지
- 업무 구역 확장 시 바닥과 벽을 고정할지, 좌석 구역만 넓힐지
- 실제 활동 로그의 업무 분류 비율을 모아 좌석 비중을 보정할지
- CEO 집무실과 기록 보관실을 공용 오피스에 어떻게 유지할지

## 디자인 배치안

`office-dimensional-layout.svg`는 외곽 크기와 업무 구역, 자리 규모를 담은 디자인 배치 초안이다. 좌표계 원점은 층 중앙 `(0, 0)`, X/Z 단위는 미터이며, 외곽 크기는 **40 × 24m**를 기준으로 한다. 이전 직선형 중앙 복도 안은 [비교용 초안](office-dimensional-layout-v1-corridor.svg)으로 보존했다.

| 구역 | 배치 의도 | 기준 자리 |
| --- | --- | ---: |
| 자료 탐색 | 서가와 검색 테이블을 섞은 조용한 코너 | 6 |
| 개발 | 여러 책상 뱅크를 둔 넓은 작업 스튜디오 | 12 |
| 실행·서버 | 장비 랙과 조작 좌석이 있는 유리벽 구역 | 6 |
| 검토·회의 | 이동식 파티션이 있는 4인 소회의 포드 3개 | 12 |
| 요청 접수·휴식 | 소파, 대기 자리, 요청 확인 스테이션이 섞인 라운지 | 6 |
| 중앙 정원·라운지 | 식재와 좌석을 둔 공용 중심 공간 | 동선/휴식 허브 |

기준 좌석은 약 42개다. 모든 업무 구역은 여러 프로젝트가 함께 쓰며, 프로젝트는 좌석을 소유하지 않는다. 개발 좌석은 여러 책상 뱅크에 분산하고 자료 탐색·서버·라운지에도 여러 소규모 포드를 둔다. 같은 포드 안에서도 서로 다른 프로젝트가 함께 일할 수 있고, 프로젝트 칩은 현재 업무 맥락을 표시한다. 협업 중인 같은 프로젝트 세션은 `projectKey`를 기준으로 회의 포드에 자동으로 모으고, 인원이 늘면 인접 포드를 이어 쓴다. 이는 별도 팀 편성이나 수동 배치를 요구하지 않는다. 업무 구역 사이를 벽으로 완전히 막지 않고 바닥 재료, 낮은 파티션, 책장, 식재와 가구 방향으로 성격을 나눈다.

중앙은 직선 통로 대신 정원형 공용 공간으로 두고, 주변을 감싸는 곡선 동선과 여러 열린 연결로를 만든다. 이 동선은 디자인 방향을 표현한 초안이며, 실제 캐릭터 이동은 모든 자리와 구역에 도달할 수 있도록 장애물을 반영해 계산한다. 최소 폭을 일괄 지정하기보다 주요 교차부와 출입구에서 캐릭터가 겹치지 않는 여유를 확보한다.

## 3D 구현 시 좌표 변경 범위

이 배치가 실제 3D로 옮겨질 때는 공간 좌표와 화면 데이터 연결을 함께 바꿔야 한다.

1. `public/office-navigation.js`: 외곽 크기, 구역 경계, 벽·출입구, 가구 좌표, 최소 42개의 고유 작업 지점을 지정하고, 각 업무 구역은 같은 형식의 포드를 추가해 확장할 수 있게 한다. 현재 작업 위치 배열은 방마다 좌석 수가 적고 반복해서 반환하므로 42명 배치에 그대로 쓸 수 없다.
2. `public/office-scene.js`: 바닥과 벽 생성, 구역 이름표, 카메라가 전체 공간을 담는 범위, 조명 그림자 범위를 새 외곽 크기에 맞춘다.
3. `public/app.js`: 기본 세션 조회를 선택 프로젝트에서 전체 프로젝트로 넓힌다. 활성 직원은 프로젝트명 칩과 함께 모두 표시하고, 프로젝트/구역 선택은 필터와 강조로 처리한다. 현재의 방당 3명·전체 11명 제한은 좌석 위치와 함께 재설계한다.
4. 이동 경로: 중앙 정원과 곡선 동선, 여러 열린 연결부를 통해 모든 구역과 좌석에 닿는지 확인한다. 혼잡한 교차부는 출발·도착 지점을 분산하고 파티션과 가구를 조정한다.
5. 카메라: 전체 보기에서는 40 × 24m 바닥과 외곽 여백을 모두 담고, 방·직원 선택 시에는 선택 위치로 확대한다.

현재 분류는 실제 회의 상태를 직접 감지하지 않는다. `plan`/`think`와 에이전트 응답을 계획·협업 공간으로 분류하고 있어, 첫 배치에서는 같은 프로젝트의 해당 세션을 함께 앉히는 시각화로 본다. 실제 회의 판별을 추가하지 않는 한 테이블 점유는 프로젝트별 협업의 근사 표현이다.

이 좌표안은 다음 구현 단계에서 검토할 출발점이다. 기존 캐릭터와 3D 오피스 스타일을 유지한 채 공간만 먼저 배치해 시각적으로 확인한다. 경로와 캐릭터 겹침을 점검한 뒤 가구와 좌석을 조정한다.

## 3D 공간 시안

2026-10-21에 브라우저에서 조작할 수 있는 [3D 공간 시안](http://127.0.0.1:4173/shared-office.html)을 추가했다. 기존 앱 상단의 **넓은 오피스**에서도 연다. 기존 `createCharacter`와 가구 생성기를 재사용해 현재 캐릭터 스타일을 유지했다.

- 중앙 정원을 감싸는 열린 연결 공간과 다섯 업무 구역을 배치한다.
- 기준 배치는 자료 탐색 6석, 개발 12석, 실행·서버 6석, 검토·회의 12석, 요청 접수·휴식 6석으로 총 42석이다.
- 12·24·42명 예시는 같은 기본 가구를 사용한다. 60명 예시는 기존 포드와 좌석을 유지하면서 자료 탐색 4석, 개발 8석, 서버 4석, 라운지 2석을 추가한다. 60명은 확장 검토용 예시이며 최종 표시 상한은 아니다.
- 일반 작업 포드에는 프로젝트가 섞이고, 회의 포드는 서로 다른 세 팀이 동시에 이용한다. 이름표와 발밑 표식으로 프로젝트를 구분한다.
- 구역·직원을 누르면 확대한다. 전체 보기, 입체/위에서 보기, 회전·이동·확대, 프로젝트 보기, 이름표와 동작 설정을 제공한다.
- **직원 동선 보기**로 선택 직원 또는 개발 직원 한 명이 가구와 정원을 피해 이동했다가 원래 자리로 돌아오는 모습을 본다. 경로는 실제 가구와 파티션 좌표를 사용한다.

위 12·24·42·60명 배치는 **둘러보기**의 예시로 보존한다. 기본 화면은 아래 실시간 연결을 적용한다. 3D의 정확한 가구·좌석 좌표는 `public/shared-office-layout.js`에 모았으며, 평면 SVG는 전체 구상 참고용으로 남긴다.


## 실제 Codex 작업 연결

넓은 오피스와 타워 오피스는 같은 `/api/state`, `/events`와 SQLite 직원 식별 정보를 공유한다. 넓은 오피스의 기본 화면은 실제 작업이며, 예시 배치는 **둘러보기**에서만 표시한다.

- `office-live-feed.js`: 서버 이벤트와 주기적 조회를 연결하고, 과거 응답이 최신 활동을 덮어쓰는 것을 방지한다. 연결 실패 시 예시 직원으로 바꾸지 않고 마지막 실제 상태를 유지한다.
- `shared-office-state.js`: 모든 활성 세션과 프로젝트별 최근 휴식 세션을 모으고, 프로젝트 키와 세션 키로 좌석을 자동 배정한다. 일반 업무 포드는 공유하고, 회의 포드는 서로 다른 프로젝트가 함께 점유하지 않도록 배정한다.
- `shared-office-layout.js`: 구역별 인원에 맞춰 포드를 더한다. 내부 여유 좌석을 채운 뒤 필요한 구역을 같은 층의 바깥쪽으로 확장한다. 기존 좌석 좌표는 유지하며 확대된 바닥을 카메라에 반영한다.
- `shared-office-scene.js`: 기존 직원 모델을 유지하면서 상태 갱신을 적용하고, 업무가 바뀐 직원은 현재 위치에서 새 좌석으로 이동시킨다. 갱신 때 전체 직원을 다시 생성하지 않는다.
- 서버는 새 직원의 식별 번호를 SQLite에 먼저 배정한다. 두 보기에서 이름, 외형, 채팅 번호를 일치시키며, URL로 선택한 프로젝트와 직원을 전달한다.

넓은 오피스에는 고정 인원 제한을 두지 않는다. 실제 입력 범위는 서버가 감지하는 최근 세션 최대 192개이며, 과거 채팅 전체를 한꺼번에 3D에 띄우지는 않는다. 비활성 세션은 프로젝트당 최근 한 명을 3D에 표시하고 모든 최근 세션은 아래 목록에 남긴다. 회의 포드는 현재의 계획·협업 분류를 근거로 하며, 실제 회의 판별은 추후 확장 항목이다.

## 업무 구역 경계

바닥 색과 함께 다섯 업무 구역의 둘레에 낮은 벽을 배치해, 전체 보기에서도 각 영역을 명확히 읽을 수 있게 한다.

- 공통 바닥 테두리: 둥근 모서리 반경 1.35m, 폭 0.2m, 바닥 위 높이 약 0.075m의 입체 띠다. 출입구에는 평평한 문턱 색상을 넣는다.
- 자료 탐색: 약 1.02m 높이의 낮은 책장형 경계.
- 개발: 약 0.92m 높이의 식재 파티션.
- 실행·서버: 약 1.48m 높이의 낮은 벽과 투명 유리 경계.
- 검토·회의: 약 0.95m 높이의 패브릭 파티션.
- 요청 접수·휴식: 약 0.82m 높이의 곡선 식재 경계.

구역마다 폭 2.6~3.4m의 출입구를 여러 방향으로 열고, 확장 구역에도 출입구를 추가한다. 경계의 위치와 장애물 정보는 같은 데이터에서 생성하므로 직원은 벽을 피해 실제 열린 입구로 이동한다. 회의 구역 폭과 확장 포드 일부의 위치는 경계와 좌석 사이의 여유를 확보하도록 조정했다. 캐릭터는 경계 위로 보이며, 중앙 정원 주변에는 열린 공용 동선을 유지한다.

## 넓은 오피스의 CEO 집무실

공용 오피스 바닥의 좌측 하단 모서리에 타워형의 CEO 전용 공간을 배치한다. `buildExecutiveSuite`를 재사용하여 약 19.8 × 14m의 원래 크기와 집무실·비서실·접견실·이사회실·서재·프라이빗 라운지·기밀문서실의 가구 및 방 구획을 유지한다.

- 전체 공간을 180도 돌려 출입구가 공용 오피스 안쪽을 향하게 한다. 엘리베이터는 타워에 남긴다.
- 왼쪽·아래쪽 외곽에서 0.8m 안쪽에 맞춘다. 휴식 구역 확장으로 바닥이 길어져도 최종 바닥의 좌측 하단에 붙어 있도록 배치한다. 검토·회의 구역과는 최소 3m의 간격을 확보하고, 필요하면 바닥을 확장해 겹침을 피한다.
- 타워와 같은 CEO·비서 캐릭터, 저장된 이름과 비서의 일별 의상, 집무실 안에서의 비서 업무 동선을 재사용한다. 일반 프로젝트 직원 수에는 이 두 인물을 포함하지 않는다.
- 공간 이름표나 사이드바의 **CEO 집무실**을 누르면 확대한다. 프로젝트 필터와 관계없이 보이는 공용 전용 공간이다.
- 벽·문짝·가구도 원래 좌표에서 함께 변환해 공용 오피스의 이동 장애물에 반영한다.
